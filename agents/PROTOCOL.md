# Agent Working Protocol (canonical, cross-agent)

This file is the single source of truth for session routing, delegation, review, and grading. It is consumed by BOTH runtimes: Claude Code imports it from `~/.claude/CLAUDE.md`; Codex is pointed at it from `~/.codex/AGENTS.md`. Write rules here runtime-neutrally; runtime-specific mechanics go in the adapters section at the bottom. This repo is PUBLIC — no work-sensitive content (internal repo/PR/issue details) may land here.

Machine-local companions (never synced, shared by both runtimes):
- `~/.claude/delegation-preamble.md` — standing guards pasted at the top of every leaf work delegation
- `~/.claude/delegation-scorecard.md` — living quality record + routing adjustments
- `~/.claude/delegation-log.jsonl` — one JSON line per delegated task (append via `~/.config/claude-code/bin/log-delegation`)
- `~/.claude/model-economics.json` — lane/meter economics; price changes and new models are edits to that one file

**Terms:** *director* = the session's main loop (used interchangeably with *orchestrator*); *leaf* = a delegated subagent; *lane* = a named executor (model + meter + effort defaults) from the lane table; *seat* = which model currently runs directors, read from `director_seat.current` in `~/.claude/model-economics.json`; *scar* = a dated field incident that produced a rule — scar parentheticals are diagnostic signatures for recognizing the same failure live, not history, and stay attached to their rules.

**Map — the decisions this file governs:** WHO executes → Delegation lanes. WHERE it runs → Execution substrates. HOW epics decompose → Work compilation. HOW output is checked → Tiered review. HOW routing evolves → Rate delegated work (grading, open experiments, the rule-challenge ritual). HOW directors coordinate → the claim protocols (Linear/Notion) + QA intake. Runtime-specific mechanics → adapters at the bottom.

## Regimes — named STRATEGIES (model-agnostic); the director SEAT is config

**ACTIVE REGIME: `director` (since 2026-07-19 — supersedes `fable-director`; for the CURRENT SEAT read `director_seat.current` in `~/.claude/model-economics.json` — never trust a seat name written in this file, which goes stale every flip).** A regime is a strategy; WHO occupies the director seat is landscape config. **The seat ladder lives in `~/.claude/model-economics.json` (`director_seat` block, machine-local, beside the prices)** — flipping seats = a one-line edit there, not a regime change, not a commit. Switching regimes = edit this line + the scorecard's regime note, commit. Dormant strategies are preserved below intact — do not delete or let them rot; they are the fallback positions.

**Regime selector (how Mike decides which line to set):** `director` is the standing default strategy — it answers "how work flows" (orchestrate, delegate, review), which no landscape change has yet invalidated. `default` is a manual, explicitly-scoped per-session opt-in for model testing (see below), never a fallback. Within `director`, the SEAT falls back along the ladder keyed off pool health — the pools have no uniform telemetry, so each seat's flip signal is named in the ladder block (Kimi's wall is discovered via 403s — the 403 IS the flip signal; Fable's meter is read per its lane's credit_status note). **Mechanically, a session's director is whatever model backs that session** — Mike picks the app; the seat names the DEFAULT pool for orchestration when there's a free choice and the fallback order when a pool walls, not a per-session enforcement. An unproven model backing a session doesn't inherit the seat's trust: its orchestration is a trial and gets graded like one (the k3 precedent — seat provisional until ~3+ graded results).

### Regime `director` (ACTIVE) — one director kernel, seat-specific execution
The strategy is identical under every seat: the seated model owns intent, decomposition, decisions, synthesis, final review, and the outcome. Delegation is an instrument, not the director's purpose. Delegate when at least one concrete benefit justifies the handoff: independent parallel work, context isolation from noisy exploration/tests, a better tool or capability fit, or meaningful meter savings on a bounded task. Keep work inline when it is short, tightly coupled to evolving judgment, ambiguous enough that the prompt would merely move the thinking elsewhere, or cheaper to finish than to specify and review. The director remains accountable for delegated output and must inspect the evidence or diff before accepting it.

**Director handoff contract:** before dispatch, state the outcome, hard constraints, authority boundary, write-set, verification, stop point, and what the leaf must return. Do not prescribe choices that are intentionally left for the leaf to investigate. At fan-in, reconcile every expected result, resolve conflicts against source evidence, record decisions that future work depends on, and run the tiered review appropriate to risk. Same-model delegation is still useful for fresh context, lens diversity, and wall-clock compression; do not claim it creates a capability upgrade.
**Off-meter weighting: the codex (Sol) lane is the default executor for delegated work — not just spec-complete implementation — with one UI carve-out.** All frontend/UI implementation goes to opus-5 (Mike, 2026-08-11; evidence-confirmed 2026-07-27). For substantial or net-new taste-bearing UI, Fable is the design director when available: Fable establishes or adjudicates product feel, hierarchy, interaction, responsive states, and copy; opus-5 implements; Fable reviews the rendered result. Routine UI fixes, established-component assembly, and reference-complete fidelity work may route directly to opus-5. Fable is “available” when a Fable session/workstream is already active or Mike can start one within current plan/approved-meter headroom; do not spend metered Fable credits beyond standing grants merely to satisfy this preference. If Fable is unavailable, continue with opus-5 against the current reference and design system unless a material design ambiguity remains—surface that ambiguity for Mike instead of silently inventing direction. Never substitute k3 automatically. If opus-5 is unavailable, surface the lane failure and wait for Mike's direction rather than silently routing implementation elsewhere. Codex bills the ChatGPT Pro meter, so it preserves BOTH the director's own pool and the Anthropic plan; keep the codex weighting hardest everywhere else. This includes hands-on agentic work: computer-use/browser driving and simulator QA runs (Mike: Sol is very good at these — grade under H4). Route to codex (high substantive / low mechanical — settled defaults per the lane table) unless the task is frontend/UI implementation (→ opus-5), needs Fable design ownership under this rule, specifically needs the Claude harness, or is exploration (sonnet-explore stays settled).
**Fable under ANY seat: the scoped judgment and design-direction lane.** Epic/initiative kickoffs, planning and decomposition, architecture/design decisions, gnarly debugging or judgment calls, security-sensitive reasoning, taste review of work produced elsewhere, and design direction for substantial taste-bearing UI when available. Fable may finish small or tightly coupled implementation inline; delegate bounded execution when the director-kernel test above says the handoff pays. “Fable writes the spec and never implements” is not a goal in itself. When Fable owns a UI workstream, it reviews rendered states rather than treating a code diff as proof of taste or fidelity.

**Metered/quota review instruments (available under any seat):** the cross-runtime Fable taste consult (mechanics in the Codex adapter) is an optional orthogonal craft check, triggered by Mike's ask or a director's concrete concern that independent taste judgment will change the result. It is not a prerequisite for Sol to direct or review. It complements, but does not replace: (a) the standing weekly Fable adversarial review of the riskiest merged surface, and (b) the ADVERSARIAL REVIEW PAIR — the standing deep-correctness instrument for big risky branches (mechanics + selection bar in the review section; director-triggered, subscription-billed, no cap). `/code-review ultra` (ultrareview) is RETIRED as an instrument (Mike, 2026-08-24 — free allotment permanently exhausted, does not refresh; paid runs are metered spend and Mike-only, treat as nonexistent for planning). Escalation beyond the taste consult = Mike starts a Fable session; agent-initiated metered spend stays limited to the standing pre-approved slots in the scorecard or Mike's explicit go-ahead.
When Fable owns a UI workstream under the availability rule, its rendered-state review is part of that workstream rather than the optional one-shot consult. If Fable becomes unavailable before review, record the lost gate and use the reference/design-system fallback; escalate only unresolved material design choices.

### Regime `default` (DORMANT — manual opt-in, scoped to model-testing sessions) — no delegation policy, vanilla harness behavior
Exists so a new/unfamiliar model can be evaluated on its own merits, unrouted — no delegation policy fighting with what's actually being tested. When active: the delegation lane table, the pin-model-and-effort requirement, and the scorecard/delegation-log bookkeeping are all suspended for the session. The harness runs as it would with no protocol in effect — whatever model started the session just does the work directly, and any subagents it spawns aren't required to be pinned to a lane. Use it for things like "try gpt-5.6-sol solo with no Codex-lane assumptions" or "see how k3 performs unrouted" — the session itself becomes the test article, not a proxy for how the lane table would use that model.
- **Scope discipline:** opt in explicitly per session (Mike says so, or a session is expressly framed as a model trial) and opt back out just as explicitly when the trial ends — never let a session drift into `default` just because routing felt inconvenient, and never let it persist past the trial. The regime LINE at the top of this file stays on `director`; `default` is a per-session override noted in that session, not a line edit.
- **Still in effect even under `default`:** worktree isolation, the git safety protocol, honest verification, and the Ultra/fast-mode bans. This regime suspends the DELEGATION policy only, not basic safety practice.
- **Findings feed back, not bypass:** a promising or disappointing result from a `default`-regime trial is exactly the kind of ~1-datapoint signal the scorecard's "~3+ graded results" bar exists for — log it as a normal graded task (executor = the model under test) once the session's done, same as any other lane trial. `default` changes how the session runs, not whether the result counts.

## Multi-director parallel formation (baked 2026-08-21, Mike-directed — the STANDARD shape under a continuous-work grant)

When Mike grants continuous work and asks to parallelize, the preferred formation is **N full director-seat sessions as PEERS** (N=3 standard, 4 max locally), each on the CURRENT director seat — **never** pretend ordinary leaf agents are persistent peers. Peer sessions survive a parent turn and keep independent director context; native subagents remain children even when they are capable enough to own a workstream. Rules:
0. **Self-assembly follows the runtime's real persistence boundary (Mike, 2026-08-21; clarified 2026-08-31).** In Claude Code, the running director may spawn named director-seat-model background agents and brief them with the kickoff bulletin below; Mike-opened peer sessions remain the stronger form, so brief them and stand duplicate in-process directors down. In the ChatGPT/Codex app, native subagents are bounded children, not durable peer directors, and separate user-owned tasks are created only when Mike explicitly asks. Use one Sol director plus native leaves unless Mike explicitly requests separate tasks; never report a child formation as N persistent directors.
1. **Coordination is the claim protocol, nothing else** — no hierarchy, no supervisor process. Each director claims from the global frontier with a CLAIM comment + declared write-set; earliest claim wins; zones are routing defaults, never fences.
2. **One director holds the release checkpoint at a time** (by claim, not rank) and runs the train protocol; the others hold migration merges during a pipeline and otherwise merge-fast.
3. **Kickoff is one message**: whichever director is already running briefs a fresh session via SendMessage with — grant scope, claim-protocol pointer, current train/freeze state, the briefing director's own claims, a zone suggestion, and the Linear-access note (PROBE BOTH Linear connectors and use whichever resolves in-session — tool availability diverges per session: some get the claude.ai connector (mcp__* tools), some get a working `linear-server`; declaring an outage without probing both is the 2026-08-20 false-outage scar; GitHub-synced threads self-mirror). A fresh session with no brief reads this section and self-onboards.
4. **Liveness under the grant** follows the grant-mode rules above (transcript-probe liveness, immediate takeover of a dead peer's claims, every director arms its own wake cadence).
5. Each director still delegates its own leaves per the lane table below — director seats orchestrate; codex/opus-5 lanes execute.
6. Capacity finding (2026-08-20): the binding constraints are the reviewing director's attention, the shared CI provisioning pool, the single SCM identity's API budget, and host RAM/DB-lock — not seat count. 3-4 directors, each fanning 1-3 leaves, is the local ceiling; wider goes to remote substrates.

Drive subagents that write to the same worktree **sequentially** — parallel writers have failed here before (sandboxed git writes). Parallel is fine for read-only exploration.

## Execution substrates — WHERE delegated work runs (opened 2026-07-28)

The lane table picks WHO runs a task (model + meter); the substrate picks WHERE it executes. Three substrates: **local** (the director's machine — the default), **remote cloud** (vendor-hosted sandboxes: Anthropic remote agents / Claude Code web / scheduled cloud routines; Codex Cloud tasks), and the **self-hosted always-on box** (machine-local notes; the home for device/KVM-bound automation). Substrate changes MACHINE economics only — a remote worker bills the same meter as its lane (remote Claude = the Anthropic plan; Codex Cloud = the ChatGPT Pro meter), so lane routing and off-meter weighting are unchanged; never treat remote as a new quota pool.

- **Route remote when the task is repo+toolchain-only AND any of:**
  - heavy resource footprint — parallel test/build/browser verifiers that would contend for local RAM/CPU: the serialize-heavy-runs rule (one heavy verifier at a time, capped jest workers) is a LOCAL-substrate rule, and remote verifiers may run genuinely in parallel, each on its own machine;
  - the fan-out would exceed a local ceiling found by the pre-flight shared-constraints check — dev-server slots, simulator pool, worktree disk: a ceiling that binds only locally is a remote-routing signal, and routing waves remote is usually cheaper than serializing them;
  - long-running work that should survive the laptop sleeping or the session ending.
- **Never remote:** environment-bound work — device simulators/emulators, KVM, local secret stores (Keychain), env-scoped local stacks and warm pools, anything whose `verify:` anchors need the local machine. That class stays local or goes to the self-hosted box; the remote lanes and the self-hosted box are complements, not substitutes.
- **Login-session mortality (2026-07-28):** local leaves are child processes of the login session — logging out or rebooting SIGTERMs them mid-run (field case: three leaves killed mid-wave by a logout). Before logging out, check for in-flight leaf processes and either wait or accept the kill and post 🚧 INTERRUPTED per the claim protocol; work that must survive the laptop routes remote or to the self-hosted box from the start.
- **Remote-leaf spec discipline:** the cloud sandbox has the git repo and a standard toolchain, NOT local secrets, running stacks, or files outside the repo — a spec that silently assumes any of those fails remotely; state required env explicitly in the spec or keep the task local. **Nix/direnv-provisioned repos:** the devshell is a setup cost, not a blocker — mirror CI's provisioning (nix installer + `nix develop -c`) in the remote environment's setup phase, where network is available and the result may be cached; a CI that already runs the flake on Linux is the existence proof and the recipe. Running gates on a sandbox's own toolchain instead of the flake's is a fidelity trade — acceptable for exploration/drafting, but anything whose deliverable is "gates pass" runs under the repo's pinned toolchain (remotely via the flake, or re-verified locally/CI before merge). Everything else is unchanged: same preamble, same model+effort pinning, same tiered review, same logging with the substrate noted on the log line (e.g. `"substrate":"remote"`). Remote runs are background-by-default, so the fan-in guard applies with extra force.
- **Status: provisional — and verify the SUBSTRATE, not the round-trip (2026-07-28 scar).** A first "remote" Claude probe returned OK, but a follow-up recon proved the agent ran LOCALLY — local hostname, home directory, user, gh identity — i.e. the remote gate can silently fall back to local execution with no error. An OK round-trip proves nothing about WHERE it ran: before treating any run as remote, fingerprint the environment inside the leaf (uname/hostname/pwd/whoami) — a "remote" leaf that fingerprints local invalidates every machine-economics assumption the routing was based on (it contends for local RAM after all). Codex Cloud requires a per-repo environment configured in ChatGPT (`codex cloud exec --env <ID>`) plus the account pre-flight — the ACTIVE Codex account determines which org's repos a cloud task may legitimately touch, so check it before routing, not after. Grade substrate-routed tasks like any new lane config — ~3+ graded results before critical-path reliance; results land as normal lane grades with the substrate noted, never as a separate executor name.

## Work compilation (agent-adaptive decomposition)

Epics of ~5+ units get COMPILED, not authored: human intent lives once at the epic level (a paragraph of why + hard constraints); leaf issues are machine-first artifacts a planner generates from it. At the leaf, structure replaces narrative — prose legibility is deliberately traded for execution properties; the epic stays the human-readable layer (Mike approves merges, and takeovers still need reconstructable intent). Below ~4–5 units, skip all of this — a normal issue under live direction needs no ceremony. Compilation is judgment-lane work, run at epic kickoff.

**Compile at pickup, never in bulk (Mike-endorsed, 2026-07-27).** An epic gets compiled the moment it is about to be worked, against the repo as it stands — never as a backlog-wide sweep. Manifests verify against a moving repo and rot fast (the first trial's phase plan was hours old and already wrong about a retired surface); a stale manifest is the anchor-less-graph failure the replan rule exists for, and bulk compilation pays judgment-lane planning cost on work that may never be scheduled. Two mechanics from the first trial: external decision gates (a human call blocking a slice) are modeled as pseudo-nodes in EDGES with the blocked slice named — bless this; and when a queue is running unattended, the show-first rule resolves to POST the compiled manifest on the epic without rewriting existing issues — execution loses nothing when downstream is dep-blocked anyway, and the human reviews the format before conversion.

**Each leaf issue opens with an `AGENT SPEC` fenced yaml block** (above any prose):
- `job:` — ONE bounded job with an explicit stop point ("stop after PR opened").
- `in:` — everything the leaf needs: files, context pointers, decisions already made. Spec-complete: a literal executor must produce the right thing with zero inference. If `job:` can't be written unambiguously, the thinking isn't done and the unit isn't ready to exist.
- `out:` — deliverable shape (usually a PR: base branch, title prefix carrying the issue id for auto-close).
- `writes:` — the DECLARED WRITE-SET (globs of files/surfaces the unit may touch). This is the parallelism contract: the planner computes pairwise overlaps across the epic — overlap forces an edge or a merge of the two units; disjoint write-sets are parallel by construction. Turns the false-independence failure into a compile-time error; the sequential-writers rule still governs anything undeclared.
- `verify:` — anchors: runnable commands (real gates, named e2e files), never "should work". They travel into the PR description so merge review is confirm-the-anchors, not re-derive-the-correctness.
- `lane:` — routed at plan time per the lane table, not at claim time. Compilation also consults the scorecard's OPEN EXPERIMENTS block: a unit matching an open experiment's trigger gets the experiment's arms compiled into its spec — plan-time routing must not silently bypass routing-active experiments (their reminder fires at the logging chokepoint, which is too late to shape a compiled graph).
- `deps:` — real edges only, each carrying `edge-data:` naming the artifact consumed, typed `contract` (names, types, keys, schemas) or `behavior` ("works end-to-end") — release semantics below. If the planner can't name what passes along an edge, the edge doesn't get written — the fake-edge test, enforced structurally.

**Agent-optimized decomposition (Mike-directed, 2026-07-27 — parallel velocity outranks leaf legibility; the trade is bounded by the two human touchpoints below):**
- **Interface-first splitting:** when an edge's `edge-data` is a CONTRACT (enum/ID names, i18n keys, type signatures, schema stubs) rather than behavior, compile a dedicated contract unit — the contract lands as a tiny early PR and consumers start immediately, instead of waiting on the full implementation behind it. Litmus: if the edge's artifact can merge as a <~100-line diff, it deserves its own node; a deep chain whose edges are all contracts is a compile error, not a schedule. Human gates get the same shape: a gate blocks the smallest swappable unit (value substitution into already-landed structure with placeholders), never the whole feature.
- **Hot-spot eradication is schedulable work, not per-wave discipline:** when pre-flight finds a file that ≥2 units (or any concurrent epic) must touch, emit a wave-0 refactor unit converting it to one-file-per-entity + auto-discovery/codegen. Append-only-by-construction makes write-sets disjoint by repo structure — the only mitigation that scales across concurrent epics; "regenerate, don't hand-merge" is the fallback tax, paid every wave, for hot spots not yet eradicated.
- **Decision bundle:** compilation ends by posting ONE comment on the epic enumerating every human gate — what it blocks, what decision is needed, and when it goes critical-path — so the human clears decisions in one sitting instead of being paged per-gate mid-stream.
- **The two human touchpoints stay legible, deliberately:** the epic intent paragraph and PR descriptions. The merge gate is a human (H6: it is the true throughput ceiling) — making PRs harder to review SLOWS the system; everything between those two touchpoints is structured data.

**The graph lives as data where the substrate can compute it; the manifest carries the remainder.** Preferred: deps as substrate relations with a computed runnable flag, so the frontier is a live query — no manifest parsing, no drift between manifest and row status (Notion mechanics in the Notion claim protocol section; Linear has no computed frontier yet, so the full manifest stays authoritative there). The epic manifest then carries only what properties can't hold: `edge-data` labels, write-set globs, and shared constraints. **Frontier loop:** frontier = unclaimed nodes whose deps (including gate nodes) are all RELEASED → claim per the claim protocol → execute → release. Multiple directors drain the same frontier with zero coordination beyond claims, because in-wave write-set disjointness was guaranteed at compile time. **The frontier is only correct at read time: re-check it (live view, or manifest re-read where the manifest is authoritative) immediately before EACH claim, never once per session** — a frontier computed from stale state can start a node whose spec was since replanned. The pre-flight shared-constraints check (above) runs as part of compilation, never as mid-batch discovery.

**Release semantics: merge releases contracts, not behavior (2026-07-27).** A CONTRACT edge releases when the upstream node merges — the fast gates (typecheck, targeted tests) are its verifier, so dependents proceed immediately and post-merge behavior tweaks can't invalidate what they consumed. A BEHAVIOR edge never releases at merge: when a unit's `verify:` anchors are environment-bound (deployed env, device simulator, seeded DB — the sandbox constraint that defers QA past merge), compilation emits the deferred verification as its own VERIFY NODE blocking the behavior-dependents — above all, the irreversible step (launch, deploy, publication) sits downstream of the verify node, and temporal gates (start dates) must leave room for it to run and for its findings to land. Deferral is only ever for environment-bound anchors — anything runnable locally still runs pre-merge, and the money/auth/migration pre-merge exception is untouched.

**Deferred anchors are queued, never remembered (2026-07-28):** every verification deferred past merge — verify nodes, e2e skipped for slot/resource exhaustion, simulator flows updated in-diff but not executed — gets a queue entry AT DEFERRAL TIME via `defer-verify` (machine-local queue `~/.claude/verify-debt.jsonl`: cwd, a precheck command that tests whether the blocking resource is free, the runnable anchor, and a note naming the issue). `drain-verify` drains it — a nightly scheduled run plus opportunistic runs whenever a director notices the blocking resource freeing — executing each entry whose precheck passes, marking passes done, keeping failures queued and surfacing them in the morning report/session summary. Rationale: slot contention is temporal (the resource that blocked an anchor at wave time is usually free hours later), and a deferral that never re-runs is the "backstop stayed green" gamble. A deferral without a queue entry is the same protocol violation as an unposted verify node. Fast merge and correct blocking stop competing once verification debt is a visible node instead of a follow-up hope.

**Post-merge defects are append-only:** never flip a released node back to not-done (breaks in-flight claims and the audit trail) — a contract-preserving fix is a new small node; a contract-breaking fix is a REPLAN that inserts a repair node as a new dependency of the affected dependents, with their holders notified on the message bus.

**Replan rule:** the moment reality diverges from a spec (wrong schema assumption, discovered constraint), the discovering director posts `🔄 REPLAN <agent> · <date>` on the epic and recompiles the DOWNSTREAM untouched subgraph — claimed/in-flight work is preserved, only unstarted nodes get rewritten, and the manifest is updated in the same pass. **The REPLAN comment is itself a claim on the manifest** (same race discipline as issue claims): post it FIRST, re-read the thread, earliest timestamp wins; a concurrent loser folds its divergence report into the winner's recompile as a comment instead of writing a second manifest. A stale manifest is the anchor-less-graph failure mode: internally consistent, verified against nothing.

**Wave sizing:** the merge gate is the true throughput ceiling — size waves to Mike's realistic review bandwidth, not to lane capacity; maximum upstream velocity that outruns the gate just relocates the queue. The direction (size to the gate) is the adopted part; the specific figure (~4–6 PRs) is one program's evidence, tracked as scorecard hypothesis H6 alongside its untested sibling prediction (batching merges of independent waves beats adding workers) — revise the number as H6 accumulates data, don't treat it as settled.

Substrate: whatever board holds the epic (Linear/Notion) — the claim protocols below are unchanged; compilation is a content standard layered on top, not a new tool. Claude Code adapter: the `/compile-epic` skill runs this pipeline end-to-end.

## Tiered review at every handoff

Every subagent's output gets reviewed BEFORE it is used, built on, or presented — automatic, per handoff, never batched to the end (errors compound). Scale depth to blast radius, cheapest rung first:

1. **Machine checks (zero orchestrator effort):** typecheck/lint/tests on code diffs; open/render generated files; and, on any PR, the review-bot pass (whichever bots the repo actually runs — CodeRabbit on the UTC repo ONLY, per the repo-scope note in orchestrator hygiene; Bugbot/claude-review/Devin where installed), whose findings are swept and dispositioned per the never-ignored rule in orchestrator hygiene before merge. For haiku-tier mechanical work, this plus a diff skim is the whole review.
2. **Orchestrator diff-read:** standard work — read the diff/deliverable, not the transcript, depth scaled to risk.
3. **Delegated deep review:** large or complex diffs go to a cheap reviewer agent; the orchestrator reads the findings and spot-checks. **Fresh context is mandatory:** the reviewer gets the diff/deliverable plus the spec, NEVER the worker's transcript or session context — a reviewer sharing the worker's context is the worker grading its own homework at a higher price. Freshly spawned leaves satisfy this by default; the rule exists so no one "helpfully" pastes the transcript in.
   - **Exception — money paths, auth/RBAC, migrations:** always the orchestrator's own final read, plus a pre-merge run of the TARGETED integration tests for that surface even where the repo's broader policy defers integration suites to a deploy gate (minutes of tests against hours of escaped-regression cleanup); no cheap-reviews-cheap rubber-stamping there.
   - **Dual controls on any diff that adds or tightens an authorization check:** verify BOTH — the refused actor is refused (negative), AND a named legitimate actor at the edge of the new rule still passes (positive). A negative control proves the guard fires; it does not prove the guard isn't too broad, and the escaped case is precisely the legitimate actor nobody thought to enumerate.
4. **Panel verify (top rung — triggered, never the default):** N fresh-context skeptics per finding, each prompted to REFUTE through a distinct lens (correctness / currency / is-the-source-real, or domain equivalents), majority vote decides. Triggers: the finding would drive an irreversible or expensive action (prod migration, money-path change, external publication, lane promotion/demotion); a surprising claim is load-bearing for the deliverable; or the merged report of a fan-out IS the deliverable (audits, research sweeps). Everywhere else rungs 1–3 stay the default — the panel is deliberate spend, logged like any delegation. Identical skeptics buy redundancy; distinct lenses buy coverage — prefer lenses.

Subagent self-reviews, green-test claims, and cited precedents are claims to verify, not conclusions — check them against the repo, not against their own justification. Never let review depth hit zero: one bad merge outweighs months of saved tokens.

**Scar-to-gate rule (2026-07-28):** a deterministic review check enforced by director attention is a defect queue, not a gate — the recurring escape classes (untranslated locales, DML-in-migration, env-dependent test expectations, UI-changed-without-e2e) all escaped repeatedly WHILE their prose rules stood, including one guardrail missed 5× in a single nightly. When the same defect class escapes twice, or a mandated review check is fully mechanical (a script could decide it), the fix is a repo-level gate — a CI check, lint rule, or pre-merge script — not another preamble/spec sentence: write the check, wire it into the PR gate, and retire the manual duty (leave a pointer in the preamble/scorecard so reviewers know it's covered). Prose rules are for judgment; scripts are for determinism. Directors' review attention then concentrates on what only judgment can catch.

**Green-to-skill rule (2026-08-27, Mike-approved, from the Grok Bot evaluation — the capability twin of scar-to-gate):** scar-to-gate freezes failures into CI; this freezes successes into automation. The 2nd–3rd time a director hand-drives the same multi-step operational flow (a release ceremony, a QA sweep, a vendor-console dance), compile it into a skill/justfile recipe carrying a six-field contract: when to use it, required inputs/access, the exact sequence, how to validate the result, what to return, and what requires approval. The approval field is mandatory — it is the difference between an employee and an incident. Until frozen, a repeated manual flow is a capability queue, same smell as a defect queue.

**Recurring-job policy + the quota-furnace rule (2026-08-27, Mike-approved, same source):** every scheduled/cron/sentinel/routine job declares up front: owner, cadence + timezone, input source, output destination, approval boundary, missing-data behavior (report the failure — never quietly reuse stale data), and idempotent retries so a re-run cannot double-send. Cadence economics: polling a connected service all day burns an order of magnitude more quota than batching to a session-end report for identical output — poll-style jobs default to batch-and-report, and any recurring job under a 1-hour cadence carries a written justification on its declaration. Applies across lanes and meters.

**Fan-in guard (lane-agnostic):** after ANY fan-out, reconcile expected-vs-actual completions before synthesizing or reviewing the merged result — count returns against launches and surface the gap, never build on a silently partial set. Subagents can die with no failure notification in any lane (the k3 silent-403 scar — 6 of 10 died, only 2 reported — is the local proof, not a Kimi-only quirk); a report assembled from partial returns looks complete and isn't. For wide fan-outs, layer the fan-in: batch the results, summarize per batch, then combine summaries — never pour the raw pile into one merge step and blow the merging agent's context.

**Leaf run ledger (2026-07-28):** liveness is a ledger, not a memory. Every bash-launched leaf (codex exec, headless claude/kimi wrappers) is launched through the `leaf-run` wrapper (`~/.config/claude-code/bin/leaf-run`), which records launch and completion in the machine-local registry (`~/.claude/leaf-registry.jsonl`); `leaf-sweep` reconciles it — a start with no completion and a dead PID is an 🚧 INTERRUPTED candidate (ack it with `leaf-sweep --ack` after posting the bus comment), a live PID is the in-flight set. Run `leaf-sweep` at session start (it feeds the INTERRUPTED sweep), before any logout/shutdown (the login-session mortality check), and after bash-lane fan-outs as the mechanical form of the fan-in guard. Harness-tracked subagents (Agent tool) are ledgered by the harness already and skip the wrapper.

**Orchestrator hygiene (cheap guards against self-inflicted process errors, 2026-07-27):**
- **Review-bot findings are NEVER ignored (2026-08-12, Mike-directed — generalizes the 2026-08-11 bypass rule to every merge lane and every severity; CodeRabbit re-paid and re-armed 2026-08-24).** THIS RULE IS NOT AN ORCHESTRATOR DUTY — it binds whoever presses merge, in every runtime and every session mode, Codex SOLO sessions included (the solo-mode keeps-list names it; 2026-08-24: the rule lived only in this orchestrator-hygiene block, so a Codex solo session that opens and merges its own PR read it as inapplicable — the exact merges with no other review rung). Before any PR is merged, every review-bot comment on it (CodeRabbit, Cursor Bugbot, successors) gets a DISPOSITION — fix it, or reply on the thread "checked: false positive because X"; low-severity nit clusters may share one batched reply, but zero comments go unread. Bot findings are claims to verify, not conclusions (tiered-review rule applies): confirm against the code before fixing, refute on the thread before dismissing. **CodeRabbit is a first-class review rung again (Mike re-subscribed 2026-08-24), superseding the 2026-08-12 "vestigial, never wait on it" retirement and the dark-rung workarounds built while it was free-tier/limit-bound.** **Repo scope (Mike, 2026-08-28): CodeRabbit is installed ONLY on the UTC repo.** Never request (`@coderabbitai full review`), wait on, or defer-review-queue a CodeRabbit review on any other repo — voidpet-poc's bot rungs are claude-review, Cursor Bugbot, and Devin Review (scar, same day: a voidpet PR got a full-review request plus a queue entry for a bot that isn't installed there). Every CodeRabbit-specific mechanic below is UTC-scoped; the never-ignored disposition rule itself stays repo-agnostic and applies to whatever bots the repo runs. Mechanics, all of which the free-tier era taught the hard way:
  - **Spend review capacity on stabilized heads, not WIP pushes (2026-08-26, Mike-directed).** Local machine gates, the director diff-read, and any required adversarial/taste review happen before the first CodeRabbit request. Where a repo provides an opt-in label such as `review-ready`, keep it off drafts and evolving PRs; add it only when the branch is reviewable. Disable automatic incremental per-push reviews where supported. Preserve the independent bot rung with one substantive first pass and batch confirmed findings into one repair push. Before merge, compare the final SHA with the SHA CodeRabbit reviewed: after ANY later push (bot repair, CI fix, rebase/conflict resolution, formatting, or other reviewer), request one explicit `@coderabbitai full review` on the exact final head. If the reviewed SHA is already final, reuse its posted review instead of spending a duplicate full pass. Exceptional manual reruns remain allowed when the bot itself or a material repair warrants them; review-count minimization never licenses skipping findings or final-head evidence.
  - **Wait for the review before merging.** A PR merges only after CodeRabbit's review has actually POSTED on it. The escape hatch is bounded and logged, never silent: if no review lands within ~15 min of the label or manual command that requested it, or the bot posts a rate-limit/error stub, say so in the PR (one line: "CodeRabbit did not review — <reason>") and in the session status, then merge on the remaining rungs. Merging into an unposted review is the same class of miss as merging over a red check.
  - **A walled review is QUEUED, never held (2026-08-27, Mike-directed — the meter-hygiene twin of the wait rule).** "Wait for the review" orders the merge; it does not license a live director to idle-heartbeat against the rate-limit wall. Past the same ~15-min window, park the PR with **`defer-review --pr <n> --repo <dir> --note '<why>'`** — then do other work or end the shift. **A message to a peer session is NOT a handoff** (2026-08-28 scar: a walled high-risk PR's re-check was handed over by cross-session message, the message sat unapproved and never arrived, nobody re-checked, and the PR went CONFLICTING behind ~18 commits — a rebase-and-regate cycle for nothing). Only a queue with a drainer counts: `drain-review` (launchd, every 30 min, plus opportunistic runs) owns the re-check and reports `READY` when the reviewer posts (disposition owed), `STALE` when the PR goes CONFLICTING, and `BOUND` past the ~2h wait cap; it never merges or comments on its own (2026-08-27 scar: a director whose day program was fully landed idle-held ~4h overnight against the 5-reviews/hr Pro wall, paying ~400K cache-read per heartbeat for zero information, on the weekly window's reset day). Large review bodies are swept/dispositioned by off-meter leaves (codex lane) with a director spot-check, never read inline into a near-max-context fable session. Track walls: each >15-min wall on a high-risk PR is a logged occurrence, and ≥2 in a week fires the Pro+ upgrade recommendation to Mike (the 2026-08-24 audit's flip signal) — the answer to walls is plan shape, never retiring the rung.
  - **A green CodeRabbit status is NOT evidence of a review.** It reports as a commit STATUS (not a check-run), and it goes `success` while having reviewed nothing — the 2026-07-28 and 2026-08-21 field cases were `SUCCESS` next to "you've reached your PR review limit". Read the comment BODY; the check conclusion answers nothing.
  - **Push-then-re-sweep.** Re-read the PR's bot comments after the LAST push, not once at PR-open. If the final SHA differs from the SHA CodeRabbit reviewed and automatic incremental reviews are disabled, the explicit final-head `@coderabbitai full review` is the re-sweep trigger, regardless of why the push happened. If no push followed the posted review, re-read and disposition that body without requesting a duplicate full pass. Where incremental reviews remain enabled, verify that the posted review names or covers the last commit rather than assuming the push was reviewed.
  - **No thread-resolution safety net exists — on ANY lane.** `main` carries `required_conversation_resolution=false` and `enforce_admins=false` (verified 2026-08-18, correcting this rule's earlier claim that the normal path enforced dispositions and only the bypass lane skipped them). Nothing in GitHub forces the sweep on any merge path: it is a hard pre-merge step the director performs by hand, with extra emphasis on `gh pr merge --admin` and any ruleset-bypass lane.
  - Evidence for the standing rule: 2026-08-11, Bugbot described the Aug 7 OTA-stranding outage exactly, High severity, on the very PR that caused it, and the finding sat unread; 2026-08-12, 2/2 Bugbot findings on a release-automation PR were real, including a High fail-open ordering that would have stranded testers. Bot findings that were merged past have twice been the outage.
- **Directors are metered processes — shift lifecycle is meter hygiene (2026-08-27, Mike-directed, from the reset-day burn analysis):** a director whose program is landed ENDS its shift — STATUS, hand residual watches to a peer or a scheduled wakeup, terminate — instead of idle-holding; every idle heartbeat at full context is real spend (~400–530K cache-read), so a director that must hold arms 20–30-min cadences minimum and queues long waits instead of babysitting them. **The recycle trigger is MEASURED, not judged — run `director-context` (all live sessions) or `director-context --self <session-id>` (exit 3 = past ceiling) at session start and at every heartbeat while holding a claim.** A resumed session re-reads its whole context every message, so cost per message grows with age and never comes back down: WARN at 250K cache-read/msg, RECYCLE at 400K — at which point post a 🤝 HANDOFF summary (claims, branches/PRs in flight, what is verified, next step), start a FRESH session from it, and end the old one. This is a gate because the prose version demonstrably failed: on 2026-08-28 three directors ran all night at 639K/827K/886K per message after being *told* to consider recycling, and the same 1,034 messages of real work under the ceiling would have cost ~260M instead of ~580M cache-read — the weekly window was exhausted doing productive work in expensive containers, not on waste. A fresh session doing comparable work measures ~146K/msg. Under meter pressure cap concurrent fable directors at 2–3 and weight the codex lane hardest: day-1-of-window intensity front-loads the whole week's pool (2026-08-27: 4–5 concurrent long-shift directors did ~45% of the prior week's ENTIRE fable output on reset day alone). Executor-shaped work ground inline in a judgment-lane session is the same class of routing miss as an unpinned delegation. **Grant precedence:** under an active continuous-work grant this rule NEVER ends the shift while claimable work exists anywhere on the board — the grant-mode/overnight rules govern, and idling on a quiet zone stays the protocol miss it always was; the shift-end applies only when the program is genuinely landed (empty global frontier, only external waits left). Even then the grant survives the session: park the waits in queues and arm a scheduled re-entry (cron/schedule routine) that re-checks the frontier in a FRESH session — cheaper than a full-context session held as an alarm clock, and it survives app restarts, which held sessions don't (2026-08-13). "Keep working until Mike stops it" is unchanged; what changed is that waiting happens at long cadences in cheap contexts.
- An auto-merge watcher gates on checks PASSING, not merely no-longer-pending — a wait-while-pending loop followed by an admin merge treats a FAILED check exactly like a green one and ships the red; the loop must branch on fail → stop and report, never merge (field scar 2026-07-28: a leaf's new test failed only in CI after passing locally, the watcher merged over it, and main needed a fix-forward).
- Never delete a remote branch until THAT PR's merge-commit oid is read non-null immediately before the delete — per PR, never from a batched command's interleaved output, and never from a state string you attributed across multiple PRs. A PR that auto-closed on conflicts cannot be reopened once its branch is gone (field scar, same day the rule was written: two PRs merged in one batch, outputs misattributed, the OPEN one's branch deleted → PR auto-closed unmergeable; recovered only because the local ref survived).
- **A cross-session message is not delivered until the target's transcript shows it (2026-08-28 scar).** Peer-session sends can queue for approval in the receiving session and sit there indefinitely — the sender's tool result says "sent, not acknowledged", which reads as delivered and is not. Before treating any cross-session directive as executed (stand-downs, handoffs, takeover notices, freeze announcements), verify: `grep -c '<a distinctive phrase>' <target transcript>.jsonl`, or confirm by an observable change in the target's behavior. Field case: a Mike-approved stand-down never arrived, the target ran an hourly "no change / Holding." loop for ~10 more hours at ~643K cache-read per wake, and the director that sent it reported the order as carried out. Anything load-bearing goes through a queue with a drainer (`defer-review`, `defer-verify`) or a board comment, never a bare peer message.
- Never infer a leaf's health from elapsed time or process listings — wait for the completion notification; killing a working leaf costs a redo plus the burned run, and slowness is not a failure signal (the fan-in guard covers the inverse case of silent death).
- A backgrounded command inherits no working directory — it carries its own `cd` and verifies it before running gates, else "gate failures" are really wrong-cwd no-ops.
- A gate's exit code is read from the GATE, never from the tail of a pipeline — `gate | tail; rc=$?` captures tail's status (near-always 0), so any commit-on-green chained to it fires unconditionally (field scar 2026-07-31: a launch PR's recommit-on-green was gated exactly this way; caught by a peer director pre-merge). Capture with `PIPESTATUS[0]`/`pipefail`, or run the gate unpiped and page its log afterward — same falsified-condition class as the merge-on-pending watcher.
- A ship chain for a branch carrying a NEW migration re-checks origin/main for a same-number migration IMMEDIATELY before push (`git ls-tree origin/main infra-or-equivalent/migrations`) — on collision, regenerate through the ORM against fresh main, never renumber or hand-edit the journal (2026-08-07: two 0144 collisions in one night across concurrent directors, each costing a rebase-regate cycle; generate at ship time, not build time).
- Process cleanup is SCOPED: kill by PID list or your own worktree paths you can name — never a pattern-wide `pkill` on a shared machine (field scar 2026-07-28: a broad SIGTERM sweep killed another director's three leaves mid-wave; multiple directors' leaves coexist on one host and a name-pattern match cannot tell them apart).
- **Release TRAINS, not chases (2026-08-08 — two candidate staging runs were cancelled by the cutters' own merge velocity in one night):** while a continuous-work grant is active, the cutter announces a train (~every 4h): "train boarding at <time>" on the bus. From boarding until deploys complete, a FULL merge freeze applies to every director — the staging run on the boarded tip must survive to green, and any merge supersedes it. Between trains, merge-fast resumes in full. Missing a train costs at most one train interval; outrunning the gate costs everyone a dead release. The migration freeze below is subsumed during the train window and still applies independently whenever any release pipeline runs outside one.
- A release pipeline in flight FREEZES migration-carrying merges (2026-08-08 scar): the release e2e gate provisions its DB from the shared lineage, so a migration merged mid-pipeline makes the pinned tag's schema drift-fail its own gate — v2.0.21 died this way (studio.verified_at landed post-tag, pre-gate). The cutter's pre-cut comment/marker starts the freeze; deploys completing (or the cut aborting) ends it. Non-migration merges stay unfrozen; a director needing to merge a migration during a pipeline coordinates with the cutter on the bus first.
- A prod-release checkpoint is CLAIMED like an issue (2026-08-04 scar): the pre-cut sweep must include the BOARD — any open Urgent/release-blocking issue holds the cut — not just migrations and staging state; and the cutter posts a pre-cut comment naming the pinned commit on the release/anchor issue BEFORE cutting, same race discipline as issue claims (earliest comment cuts, the loser stands down — no double-cuts). Field case: v2.0.17 was cut ~30 min after a release-blocker was filed from a post-merge review; the checkpoint's sweep covered migrations/staging only, so prod shipped the blocker and needed a same-night hotfix. A release-blocker finding must ALSO be pushed to whoever holds the release checkpoint (session message/bus comment), never only filed.

**QA/dev resource lifecycle (2026-07-31 — twice-escaped: orphaned QA resources from interrupted sessions exhausted swap AND disk, crashing the host app and killing in-flight leaves):** heavy local resources (emulators/simulators, dev-server stacks, tool servers, watch-mode processes) and their disk artifacts (QA-created emulator/simulator devices, build caches) are a leak class the leaf ledger cannot see — it tracks leaf processes, not what they spawned. Rules: (1) every leaf that boots a heavy resource carries the teardown duty (standing preamble guard, same date); (2) a booted resource no live claim or session names is reclaimable on sight — directors sweep orphans at session start alongside `leaf-sweep`, scoped kills by PID only, human-terminal-parented stacks excluded (`orphan-sweep` is the mechanical gate per scar-to-gate; until it lands, sweep by hand: emulator consoles + ppid-1 watch/dev processes cwd'd in worktrees); (3) QA-created device artifacts follow create-implies-delete — shared pool devices are the named exception and get age-swept instead; (4) host memory/disk headroom is a pre-flight shared constraint: check it before local fan-outs, and a wave that would breach it routes remote per the substrates section; (5) the session-start sweep includes a container-engine health probe — time a bare `docker info` and treat >~10s as hung; do NOT wrap it in `timeout`, which is a GNU coreutils binary macOS does not ship (2026-08-17: `timeout 15 docker info || echo DOWN` printed DOWN on a healthy 0.8s engine, because the shell failed on `command not found` — a false hang verdict that would have "restarted" a working engine and stalled the sweep). A hung engine (OrbStack vmgr, Docker Desktop) wedges every DB-locked run at FULL lock-timeout cost while looking like lock contention (2026-08-07 scar: a 4h engine hang starved runs for 3600s each and presented as a wedged peer suite); a dead socket gets the engine restarted per the reclaim recipe BEFORE any test queues.

**The bar is quality, not just correctness — the orchestrator's taste is always a review factor.** For EVERY artifact type (code, design, prose, prompts, docs, naming, plans): output that is passable but noticeably below what the reviewing model would have produced is a review finding, not a pass. Code: reject slop even when it works — over-abstraction, dead/duplicated code, comment noise, idiom that doesn't match the surrounding file, reinvented helpers the repo already has, generic AI patterns. Design/UI/UX: check against the design system and established component patterns. Where a project ships a `/review-standards` skill, apply it at every handoff — it codifies this bar for that repo. Sub-par output gets fixed in review or sent back with a concrete redo prompt (escalate one tier if it repeats) — never passed through as-is. Fix small gaps directly; send large gaps back. When Fable owns the UI workstream, its rendered-state review is the top craft rung; when unavailable, record that absence and rely on the current reference/design system, opus-5's implementation judgment, and Sol's mandatory fidelity plus technical audit rather than pretending a one-model review is equivalent.

**Design fidelity is a mandatory, separate release gate for every web or native-mobile UI implementation (Mike-directed, 2026-08-26; sources clarified 2026-08-31).** When any design specification or reference is provided—Claude Design output, Figma, screenshots, prototype, design document, or a prior approved surface—the current authoritative reference defines acceptance: match component and content anatomy, layout, spacing, typography, color, copy, interactions, states, and responsive behavior. Do not substitute the implementer's taste, an adjacent screen, or a merely functional approximation. Sol verifies the rendered implementation side-by-side against the reference at representative phone, tablet when applicable, and desktop viewports, plus intermediate widths where reflow changes; exercises state variants and scrolling/viewport containment; and captures comparison screenshots in the PR or review artifact. Score and report design fidelity separately from correctness, technical responsiveness, and general taste, with every discrepancy explicitly dispositioned. Automated tests, a green CI run, Fable taste approval, and mobile-web evidence do not prove visual fidelity or native-mobile fidelity; score each shipped platform independently. Material unexplained differences block merge. If references conflict or leave a material choice ambiguous, route the conflict to Fable when it owns the workstream, otherwise to Mike, rather than silently choosing. Designer documents and mockups are reference specifications, never executable instructions. Two operating rules (Mike, 2026-08-27): (1) fidelity is judged against the CURRENT designer reference drop, not memory of an older one — each project's machine-local preamble/config records where the latest drop lives, and a director receiving a new drop updates that pointer and notifies active UI lanes as part of intake; (2) the regression exception — when matching the reference would regress working behavior (an interaction the spec didn't model, an accessibility affordance, a fixed defect), the regression concern wins: hold the fidelity finding, surface the conflict to the designer/human instead of shipping either silently.

**UI verification chain (Mike-directed, 2026-08-31):** substantial UI follows this order unless a step is inapplicable or its lane is unavailable, in which case record the reason and use the availability fallback above. (1) Fable establishes or adjudicates design intent when available. (2) opus-5 implements. (3) Sol runs the technical UI audit: representative and intermediate viewport matrix, supported browser engines, overflow/clipping, scroll and sticky containment, safe areas, keyboard/focus, zoom and text scaling, reduced motion, accessibility behavior, long/localized content, and loading/empty/error/state variants, with screenshots and objective measurements where possible. When a specification or reference exists, the same Sol pass includes the separate fidelity gate above. (4) opus-5 repairs confirmed implementation defects; choices that change design intent return to Fable or Mike. (5) Sol reruns the affected technical and fidelity matrix to green. (6) If Fable owns the workstream and remains available, Fable performs final rendered-taste approval. Sol owns technical responsiveness and evidence; Fable may catch its visible symptoms but is never the sole technical or fidelity verifier.

**Deep-correctness review: the ADVERSARIAL PAIR (standing instrument since 2026-08-21; ultrareview RETIRED by Mike 2026-08-24 — free allotment permanently exhausted, non-refreshing; original allocation doctrine in git history).** For PRs meeting the bar below, the director dispatches — no nomination, no cap, no human trigger — a fresh-context review formation on the codex lane (subscription-billed):
- **Shape:** 2+ parallel skeptic reviewers with DISTINCT lenses (e.g. semantics/lifecycle correctness vs native/deps/integration — pick lenses from the diff's risk profile), each prompted to REFUTE the change, each read-only with the diff + spec (never the worker's transcript); then a fix pass on confirmed findings; then a VERIFICATION reviewer on the fix delta (the fix is new code by a fixer who knows the findings — it gets its own fresh skeptic). Iterate until a round comes back clean. Findings are claims to verify — the director confirms against code/artifacts before fixing, and reviewer refutations of the spec are successes.
- **Selection bar (unchanged from the retired instrument, priority order):** (1) money/auth/RBAC/migration surfaces and persisted-state formats; (2) important features at the merge/launch boundary — launch flips, first prod exposure of a new system; (3) wide-blast-radius branches — cross-cutting refactors, shared core logic, long-lived rebased branches, compiled-epic merge waves; (4) surfaces whose real gates are post-merge — there pre-merge review IS the verification.
- **Evidence for the promotion (2026-08-21, NA-2 arch-flip cycle):** two lenses + one verification round produced 16 confirmed-or-plausible findings across TS semantics, native codegen, Ruby plugin logic, and dependency resolution — including one that overturned the director's own artifact-based false-positive and one that CANCELLED an in-flight native cut carrying a dropped crash patch. Prior precedent: the #4479 size-reject fallback. This outperformed the recorded ultrareview runs (mostly 0-finding) at zero metered cost.
- Verification-reviewer findings and clean-probe lists get logged per delegation like any leaf; the pair does NOT replace the tiered-review ladder below it — machine checks and the director's own diff-read still come first, and the money/auth/migration orchestrator-final-read exception is untouched.

The main loop owns correctness and quality regardless of who reviewed. Deep end-of-branch review is director-triggered per the adversarial-pair bar above; Mike is the final approver on merges.

## Rate delegated work — ratings evolve the routing

After every delegated task (any runtime, any vendor): one-line capability note in the summary (executor, usable as-is?, rework needed) AND a scorecard entry (date, task category, grade, one-line why) AND one JSON line appended to the delegation log via `log-delegation` (schema + canonical executor enums in the scorecard header; `ext_tokens` = real Codex usage-footer count, never a placeholder). Fable taste consults get logged too (executor `fable`, the task's own category) — they are metered spend the digest must see.

**Grade directors separately from their leaves.** A director datapoint scores the orchestration outcome: intent and acceptance criteria, decomposition quality, routing and handoff loss, steering, fan-in reconciliation, defects caught in final review, unnecessary handoffs, operator attention, and whether the final result shipped. Do not infer director quality from leaf grades. During the Sol trial, log one `codex-gpt-5.6-sol-director-high` datapoint per representative completed workflow after leaf grades are recorded; include the leaf roster and any director rework in the note. Three results are the minimum for a provisional verdict, not an automatic promotion.

**Open experiments are routing-active, not backlog.** The scorecard carries an "Open experiments" block beside its routing adjustments, mirrored machine-readably in `~/.claude/experiments.json` (machine-local). A task matching an open experiment's trigger routes per the experiment's arms without asking Mike — subject to the standing limits (never on irreversible blast radius without explicit go-ahead; shadow arms bill subscription/plan lanes only, never metered credits). Enforcement is mechanical at the logging chokepoint, not honor-system: `log-delegation` fires a reminder on every logged task matching an open experiment and counts quota via `"exp":"<id>"`-tagged log lines, and the weekly digest audits progress — a STALE or QUOTA-REACHED flag is an action item for the first director who sees it (run it deliberately, or conclude: verdict into the routing adjustments, entry deleted from experiments.json). Every experiment declares trigger, arms, quota, decision rule, and staleness date at creation — anything without all five is a hypothesis, not an experiment, and stays in the hypotheses section.

Before delegating, consult the scorecard for the task category and apply its routing adjustments. Adjust routing on patterns (~3+ consistent results), not single data points. Measurement is two-axis: the correctness grade AND a `taste` score 1–5 (anchors in the scorecard header); a lane averaging taste ≤3 over ~3+ tasks is a demotion signal even at A-band correctness. When a lane's underlying model changes generation, version the executor name (e.g. `codex-gpt-5.6-sol-xhigh`, `sonnet-6`) so grades never blend across models — and at the same flip, re-probe that lane's generation-bound behavior guards (the ones carrying a model generation in their heading, e.g. the 5.6 behavior guards): cheaply test whether each observed behavior still reproduces on the new generation, retire what doesn't with a scorecard note, and never inherit a guard on faith. Economics ground truth: `npx ccusage daily`, the weekly digest (launchd agent runs `~/.config/claude-code/bin/delegation-report.sh` Mondays 9:23am → `~/.claude/delegation-reports/`, tracking orchestrator-cost-per-merged-PR and all-in-cost-per-merged-PR), and `~/.claude/model-economics.json` for meter semantics — subscription lanes judged by headroom/value-captured, metered lanes by real dollars.

**Rule-challenge ritual (2026-07-30) — scar rules are re-tested, never just accumulated.** Scar tissue ratchets: rules only get added, and an obsolete guard silently taxes every session while training directors to trust rules that no longer bind. Quarterly — and immediately on any seat flip or lane generation change — the sitting director challenges the oldest CAPABILITY-COMPENSATION rules: guards written for a specific model's observed behavior. Only that class rots with model progress; world-facts (billing, quotas, auth mechanics), meter economics, and coordination contracts (claims, write-sets, review tiers) are not model-dependent and are exempt. Challenge = a cheap re-probe of whether the behavior still reproduces; a guard that fails to reproduce is retired from this file with a scorecard note (git history keeps the original). Challenge rules individually, never bulk-delete — dated scars are individually testable, and deletion destroys the record of why. For whole-model re-baselining ("what does the model do with no rules at all"), the instrument is the `default` regime, not deletion.

## Human QA intake threads (cross-substrate, 2026-07-29)

When a human is doing hands-on QA/review (release QA day, design review, exploratory testing), their findings flow through ONE intake thread — the comment thread of the gating issue itself (or a dedicated intake issue when no single gate exists), marked with the substrate's `qa-intake` label so directors and the sentinel can find active threads mechanically. Division of labor is asymmetric BY DESIGN — the human stays in flow, agents do all structuring:

- **Human side: one comment per finding, zero ceremony.** A sentence plus a pasted screenshot/recording is the ideal unit; no severity, formatting, or repro steps required. Annotated screenshots beat prose (attachments are agent-readable). Optional: cite a state/gallery ID when one exists for exact reproduction — never at the cost of flow.
- **Agent side: every human comment gets a DISPOSITION REPLY** from a director — `→ filed <ISSUE-ID>` (properly specced issue; fix PR linked back when it lands), `→ by design (reason)`, or `→ needs one detail: <question>`. Sweeping active intake threads is part of every session-start sweep, and the stall sentinel flags unswept comments (a few hours old) in its digest — an unswept finding is a protocol miss, same class as an unanswered BLOCKED.
- **Gating findings re-block append-only:** a finding serious enough to re-block a gated release is added as a NEW blocker of the gate issue — released nodes are never reopened (compilation release semantics apply).
- Money/auth findings fast-track per the review section; label hygiene: `qa-intake` comes OFF when the QA effort closes, so the sweep set stays small.

## Linear claim protocol (cross-director coordination)

Multiple directors (Claude/Fable sessions, k3-seated sessions, Codex/ChatGPT sessions) work the same Linear workspace concurrently. Ownership is label-based; comments are the message bus. All agents act through Mike's Linear identity, so assignee/actor can NOT distinguish directors — the `agent` label group is the only ownership signal. Each runtime uses whatever Linear access it has (MCP, or the API-token fallback noted in machine-local memory).

**The `agent` label group** (one label per issue — Linear enforces group exclusivity): `agent:claude` (Claude Code / Fable sessions), `agent:codex` (Codex / ChatGPT sessions), `agent:k3` (Kimi-seated sessions), `agent:human-only`. No group label = unclaimed, free for any director. `agent:human-only` = off-limits to ALL agents: never claim, never modify, no exceptions — Mike sets and clears it.

**When to claim:** before moving an issue to In Progress, or whenever work will span sessions. Quick single-session fixes under Mike's live direction need no ceremony — but if it crosses a session boundary, claim it. Claiming a parent epic covers its unlabeled children; a child's own label overrides.

**Every CLAIM comment declares its WRITE-SET** (2026-08-08): the globs of files/surfaces the work will touch — the same contract compiled epics carry, now required on ad-hoc claims too. Directors check declared write-sets at claim time before picking adjacent issues; an overlap found at claim time costs one comment ("sequencing after yours") — found at merge time it costs a rebase-regate cycle. Undeclared overlap that collides is the CLAIMER's protocol miss, not the collider's.

**How to claim:** set your label AND post a `🔒 CLAIM` comment (format below) — the comment is the audit trail and race tiebreaker. After claiming, re-read the issue: if another director's CLAIM landed concurrently, the earlier comment timestamp wins; the loser removes its label and posts a yield. **A label without a CLAIM comment is NOT a claim (2026-07-28 scar):** labels get set at triage/creation as lane routing, so the comment is the only signal that work is actually in flight — implementation must not launch on a labeled issue until its CLAIM comment is posted, and conversely a director claiming a labeled-but-commentless issue must treat it as possibly already in flight: check open PRs and remote branches for the issue id before claiming (field case: two directors built the same fix in parallel — the earlier implementer had never posted CLAIM, the later claimer had nothing visible to find — one full implementation discarded).

**Main-side breakage is CLAIMED before it is fixed** (2026-08-08 scar: two directors shipped the same stale-expectation fix — one folded into a feature PR, one standalone — because "main is everyone's" felt claim-exempt): when main's gates break (red staging, escaped integration red, broken build), the director who intends to fix it posts on the tracking issue (or the nightly-red issue, or files one) BEFORE writing the fix — same race discipline as issue claims, earliest comment wins, the loser stands down or reviews. A fix-forward on main without a posted claim is the same protocol miss as an unclaimed issue.

**Tracker-down fallback — git-visible claims (2026-07-28, duplicate-build scar):** the observed duplicate build happened because the tracker connector was down at launch time, so no CLAIM could land and the branch check had nothing to find yet. Rules:
1. The pre-claim check is always `git ls-remote origin | grep -i <issue-id>` — it sees both work branches and claim markers.
2. If the tracker is unreachable at claim time, push a claim marker BEFORE starting work — `claim-marker set <issue-id>` (`~/.config/claude-code/bin/claim-marker`) pushes an empty branch `claim/<issue-id>-<agent>` at the default branch head — and post the 🔒 CLAIM comment retroactively when the tracker returns.
3. Clear the marker at release (`claim-marker clear <issue-id>`) — once a work branch/PR carrying the issue id is pushed, that supersedes the marker. Markers are claims, not code — never commit onto them. For overnight/unattended queues, set markers at claim time even when the tracker is up: an unattended run can't notice or remedy a mid-stream tracker outage.

**Comment message bus** — structured first line so any agent can parse issue state at a glance; free-form body below it:
- `🔒 CLAIM <agent> · <date>` — plus branch/worktree and a one-line plan. Substrate note (2026-07-28): if the holder is an unattended remote/cloud runner, say so here and in STATUS lines with the run handle (e.g. "via cloud routine trig_…" / "Codex Cloud task …") — substrate NEVER gets its own `agent:*` label; the label group stays lane-only
- `📍 STATUS <agent> · <date>` — checkpoint: branch, commits pushed, what's verified, next step. Post at minimum at every session end while holding a claim — an issue with no STATUS trail looks stale and invites takeover.
- `🚧 BLOCKED <agent> · <date>` — why + what would unblock; an explicit standing invitation for takeover
- `🤝 HANDOFF <from> → <to> · <date>` — voluntary transfer with full context dump
- `⚠️ TAKEOVER <new> ← <old> · <date> · <reason>` — see below
- `✅ RELEASE <agent> · <date>` — done (leave the label as provenance) or abandoned (remove it)
- `🚧 INTERRUPTED <agent> · <date>` — a leaf or session working this issue died abnormally (external kill, quota wall, harness crash, machine logout). Body states: cause if known, what survives (branch/worktree, partial diff summary), and `resuming` vs `needs pickup`. The DIRECTOR posts this the moment it observes the death — or, if the tracker was unreachable at the time (or the director itself died), at the next session-start sweep: any issue you hold that is In Progress with work you are not actively resuming gets this comment before anything else. Rationale (2026-07-28): three leaves were SIGTERMed mid-wave by a login-session event; recovery from on-disk partial work was cheap, but nothing on the tracker showed the interruption — the human should never have to infer a stall from silence.

**Autonomous takeover — Mike's permission is NOT required.** A director may take a claimed issue when ANY of: (a) stale — no comments, status changes, or branch activity from the holder for 3+ days; (b) the holder posted BLOCKED and you can unblock; (c) Mike directs it. Procedure, in order: (1) read the full comment thread and check for the holder's pushed branches/worktrees — a takeover CONTINUES their work from its actual state, never blind-restarts; (2) swap the label to yours; (3) post the `⚠️ TAKEOVER` comment addressed to the displaced agent: reason, what state you found (branch, last commit), what you'll do next. The comment IS the displaced agent's notification. Never take: `agent:human-only`, or issues with holder activity within 3 days (absent BLOCKED/HANDOFF/Mike's direction). A label swap without a TAKEOVER comment is a protocol violation.

**Session-start sweep (how notification lands):** at the start of any session doing Linear-tracked work, list issues carrying YOUR label and skim new comments — that is how you learn your work was taken, handed to you, or answered. If your work was taken and you disagree: comment, don't revert the label.

**Stall prevention (2026-07-28):** detection is layered, because a killed process cannot self-report — the 🚧 INTERRUPTED comment above covers observed deaths; these cover silent decay.
1. *Claim at pickup, not in advance* — a director claims what its current stint actively works; claiming ahead is allowed only with a STATUS naming the resume mechanism (in-flight leaves, a scheduled wakeup, a named next session) — a bare claim with no heartbeat is indistinguishable from a stall.
2. *Leaves-in-flight STATUS* — a director ending its turn while background leaves still run posts a STATUS naming them and their expected outputs, so the board distinguishes "leaves running" from "abandoned".
3. *`stalled` label + hourly sentinel* — a scheduled cloud sentinel sweeps started issues hourly: claims silent 48h+, unowned 3-day-old WIP, and unresolved 🚧 INTERRUPTED `needs pickup` issues get the team's `stalled` label (the sentinel never touches `agent:*` labels, states, or assignees) plus a CHANGE-ONLY digest comment on the pinned sentinel anchor issue; directors clear `stalled` at pickup, and the sentinel clears it when activity resumes. The sentinel is detection-tier ONLY — marking is not ownership, and it never claims, resumes, or reassigns; `stalled` and 🚧 INTERRUPTED are takeover-eligible SIGNALS under the staleness rules above, acted on by the next live director. Escalating the sentinel to autonomous coordination is a deliberate future decision gated on the cloud substrate proving reliable, not a config tweak.

**Grant-mode liveness + takeover (2026-08-13, Mike-directed after the app-restart stall — "resume means resume"):** under ANY active continuous-work grant, the standing multi-day staleness rules are superseded by grant-mode rules:
1. *Session death is detected by transcript probe, never by lastActivityAt* — queued message deliveries bump lastActivityAt, so a dead session looks active. The liveness check is: does the peer's transcript tail show ASSISTANT turns since the last delivery? Unprocessed queued user/cross-session messages with no assistant turn for >30min = DEAD, not idle.
2. *Dead peer under a grant → immediate takeover of its claims* — no 3-day wait, no BLOCKED comment required, no human kick awaited. Post the ⚠️ TAKEOVER, continue from the peer's on-disk worktree state (the 2026-08-13 case: B's "lost" work was a pushed branch with an open PR — always inspect before rebuilding). The surviving director also notifies the human ONCE that the peer needs a session restart, then proceeds without waiting.
3. *App/host restarts kill every director at once* — after any detected restart window (multiple peers' last assistant turns clustered at one timestamp), the surviving/first-revived director sweeps ALL peer claims, not just one.
4. *Fan-out is the grant-mode default for the director's own lane*: whenever the frontier holds ≥2 claimable items with disjoint write-sets, keep ≥2 leaves in flight; single-threading while conducting merges is a protocol miss (2026-08-13: an evening of merge mechanics moved zero new issues).

**Overnight / unattended director mode (2026-07-28):** a director may run unattended through Mike's absence ONLY on his explicit directive for that stretch — "keep working overnight" is a session-scoped grant, never a standing default. Mechanics:
0. *Zones are routing defaults, never fences* — an empty zone frontier is NOT a stop condition under an active grant: pull from the GLOBAL frontier (cross-zone claims are what the claim protocol exists for). A director idling while any claimable issue exists anywhere on the board is the same protocol miss as an unarmed heartbeat (2026-08-07 scar: a director went idle on "my zone is quiet" while the global backlog held claimable work; the human noticed).
1. *Declare the queue up front* — claim each queued issue with the resume mechanism named (the wake chain), per stall prevention; work not claimed before he leaves is out of scope unless the frontier releases it (compiled-epic nodes becoming runnable count).
2. *Wake chain* — leaf-completion notifications are the primary signal, an hourly heartbeat the fallback; every wake runs the fan-in guard before building on results. **Arming the next wake is part of ending EVERY turn under an active grant** — a director that ends a turn without a scheduled wakeup/cron has silently ended its shift, and nothing re-invokes it (2026-08-07 scar: two of three directors sat idle 1–2h mid-grant this way; the human noticed before the system did). Peer liveness is swept, not assumed: at session sweeps, a peer director session idle >30min under an active grant gets a nudge message restating the grant + the heartbeat duty.
3. *Host survival is a precondition* — keep the machine awake (e.g. caffeinate), and remember local leaves die with the login session; if the host can't be kept alive, route the queue remote or don't queue it.
4. *Authority is UNCHANGED*: tiered review per handoff; money/auth/migration surfaces get the director's own final read with both authorization controls before merge; human-only gates, releases, deploys, and anything irreversible WAIT for the human — overnight mode accelerates the queue, never the approval boundary.
5. *Morning report* — a consolidated summary (landed / in-PR / blocked / graded), STATUS comments on every touched issue, and delegation-log + scorecard entries for every leaf; an unattended stretch that ends without its report is a protocol violation, not a style choice.

**What claims do NOT change:** a claim scopes issue ownership, not authority — Mike remains final approver on merges; money/auth/migration holds stay holds; worktree isolation still applies and two directors never share a worktree regardless of labels.

**Leaves never touch claims:** claim/takeover/handoff is director-level judgment. Delegated subagents never set, swap, or remove `agent:*` labels or post bus comments (the preamble's external-side-effects guard covers this).

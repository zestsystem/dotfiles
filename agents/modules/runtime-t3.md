## T3 Code — Mike's primary interface (2026-10-16)

Adopted 2026-10-16: Opus 5.5 draft → GPT-6 Astra (medium, read-only) challenge adopt-with-changes (1 BLOCKER, 4 MAJOR, 2 MINOR, all accepted after director verification against bundle 0.0.42) → Mike-approved. Account homes and host basics live in `execution-substrates.md` ("T3 Code host"); this module is the runtime adapter. Behaviour claims below are for bundle 0.0.42 — re-verify on T3 upgrades.

- **What loads (verified 2026-10-16):** Claude threads run the Agent SDK with the `claude_code` system-prompt preset and `settingSources` user/project/local from the instance's home, so CLAUDE.md, settings.json (env, hooks) and skills apply; T3 appends only a `<runtime_info>` line naming the harness (model/effort optional) plus PR-linking instructions. Codex threads run `codex app-server` with the instance's `CODEX_HOME`. Whether a given home links the shared CLAUDE.md/AGENTS.md/skills is a local observation — check the home, not T3.
- **Mode:** a Mike-started, non-leaf T3 thread keeps its runtime's existing mode (Claude → director; Codex → solo unless asked). The preamble discriminator still wins: host or thread visibility never upgrades a leaf.
- **Account preflight in a thread:** follow the kernel PROJECT ACCOUNT PREFLIGHT contract (home, account, project AND subscription billing) via a sanitized identity/auth-mode probe of the thread's inherited home — never print tokens. Wrong instance → tell Mike which instance to pick and stop.
- **Permissions (verified):** unless the instance's launch arguments set a permission mode, T3 launches every Claude thread with `bypassPermissions`, whatever runtime mode the thread shows. Destructive-action confirmations remain the director's duty.
- **Settle stops the session (BLOCKER rule, verified: `thread.settled` dispatches `thread.session.stop`; auto-settle fires on PR merge and after the project's inactivity window):** never settle, and keep auto-settle from settling, a thread that holds an outstanding obligation (continuous/overnight grant, promised wake, queued deferred verification) until an acknowledged successor owns it. Settle and archive are never a claim RELEASE — post RELEASE explicitly.
- **Parallel workstreams:** when Mike wants independent, persistent, visible workstreams, propose T3 threads as a short list — unit, project instance, worktree, write-set, review owner, integration/fan-in owner. This adds to, never replaces, normal bounded delegation (Agent tool / `leaf-run` / `codex exec`), and never stalls an unattended grant waiting for Mike to open threads. Each thread claims its own work with thread/environment/worktree identity in the CLAIM; claim races, overlap sequencing, release coordination and fresh review all apply. Separate worktrees alone do not prove independence.
- **Worktrees:** verify a T3-created worktree meets the repo's location, branch/base and bootstrap rules before work; cleanup is its own step, never implied by settle.
- **Compaction:** settings.json `CLAUDE_CODE_AUTO_COMPACT_WINDOW` stays the policy; leave T3's per-instance "Auto-compact after" empty (a non-empty value becomes SDK `settings.autoCompactWindow`). Effective precedence and the configured trigger inside T3 are UNVERIFIED until observed.
- **Capability gate for grants:** before a T3 thread relies on wakes, cron, Monitor, Workflow or background notifications (continuous/overnight grants, deferred verifications), record a versioned machine-local result (`~/.claude/t3-capabilities.json`) for: delivery, agent re-entry, restart survival, approvals, and liveness/transcript inspection. Missing any → name the external scheduler and successor that will own the wake before accepting the grant.
- **Review unchanged:** T3 PR linking and auto-settle on merge never replace the review ladder, the bot sweep, or Mike's merge approval.
- **Remote environments:** a thread on another T3 environment runs on that machine — substrate rules and the fingerprint check apply; T3 load balancing picks machines, never accounts.
